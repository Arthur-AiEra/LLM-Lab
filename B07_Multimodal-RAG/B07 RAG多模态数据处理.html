01. PDF 解析：RAG 的“埋骨地”

PDF 是非结构化数据的核心，但也是最难处理的格式。传统 Text-based RAG 遇到以下情况会失效：

  • 复杂排版：双栏、跨页表格、页眉页脚干扰。
  • 视觉信息：趋势图、流程图、带有语义的截图。
  • 表格崩坏：PDF 转 Markdown 时，复杂嵌套表格往往变得不可读。
⚠️ 结论： 单纯的 OCR 或 Python 库（如 pypdf）会丢失大量“空间语义”。

02. 两条主流技术路线

维度 路线 A：Pipeline RAG (硬解析) 路线 B：Visual RAG (ColPali)
原理 OCR/版面分析 -> 提取文本 -> 图片转Caption -> 存入向量库 Screenshot -> Vision Encoder -> Multi-Vector -> 视觉检索
工具 Unstructured, Marker, Surya, VLM (GPT-4o) ColPali (ColBERT + PaliGemma)
优点 Token少，对纯文本友好，技术栈成熟 所见即所得，完美保留图表、表格、排版语义
缺点 信息损耗大，流程复杂，Caption 往往丢失细节 索引体积大（多向量），检索延迟略高

03. ColPali：视觉检索的革命

ColPali 不再将 PDF 视为文本流，而是视为图片流。

  • Vision Encoder：使用 Google 的 SigLIP 或 PaliGemma 将页面截图编码为 Patch Embeddings。
  • Late Interaction (ColBERT)：
    • 不将整个页面压缩为一个向量（Bi-Encoder），而是保留所有 Patch 的独立向量。
    • MaxSim 算法：Query 的每个 Token 向量与页面的所有 Patch 向量计算相似度，取最大值后求和。
  • 优势：精准定位到页面中的具体“角落”（如左下角的图表），无需人工切片（Chunking）。

💡 课堂精华 Q&A

Q1: 为什么 ColPali 比传统的 OCR+Embedding 效果好？
OCR 只是把字识别出来，丢掉了“位置关系”和“视觉样式”（如加粗、颜色、表格线）。ColPali 是基于视觉的，它能像人眼一样理解“这个标题下面跟着这个图表”，保留了完整的上下文语义。
Q2: ColPali 的索引体积会不会很大？
会。 因为它使用了 Multi-Vector（多向量）存储。一张页面可能会生成 1024 个 Patch 向量，比传统的一个页面一个向量大得多。需要权衡存储成本和检索精度。
Q3: 实际工程中如何落地多模态 RAG？
推荐混合检索： 1. 粗排：使用关键词（BM25）或轻量级文本向量快速召回 Top-50 页面。 2. 精排：使用 ColPali 对这 50 个页面的截图进行视觉重排序 (Rerank)。 这样既保证了速度，又利用了视觉语义。
Q4: PDF 中的跨页表格怎么处理？
这是硬解析的噩梦。但在 Visual RAG 中，可以通过多页拼接（Concatenate Images）或者依靠模型的上下文窗口，将连续的两页截图同时喂给模型，让 VLM 自动关联上下两部分的表格。
