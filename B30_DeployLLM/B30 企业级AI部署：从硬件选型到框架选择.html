✅ 企业级AI硬件选型

1. CPU vs. GPU

  • **CPU**: 擅长复杂逻辑控制与顺序指令（数十核心单核强），在推理中负责并发请求调度、Tokenization、正则过滤等前后处理 [cite: 26, 115]。
  • **GPU**: 专为并行矩阵运算设计（数千核心），如 H100 拥有 **16896** 个 CUDA 核心，能同时执行大量简单运算 [cite: 28, 29]。

2. LLM 的矩阵运算

  • **机制**: 文本转为高维向量，输入句子堆叠成矩阵（如 100个Token 形成 $100 \times 4096$ 的矩阵）。注意力机制本质是 Query矩阵 $\times$ Key矩阵 [cite: 36, 38, 39]。
  • **Embedding**: 本质是 `LLM + 池化层(Pooling)`。提取 Token 矩阵特征并压缩为单个句向量（用于语义检索） [cite: 51, 55, 56]。

3. LLM 推理中的数据搬运 (内存墙)

大模型推理 **90%** 的时间在等待数据搬运，而非计算。2026年选型逻辑已转为带宽优先+容量优先 [cite: 69, 70]。

  • **SRAM (芯片内)**: 聚合带宽 **40TB/s**，极快但极小，用于线程间数据复用（Tiling）和共享 [cite: 65, 76]。
  • **HBM (芯片外显存)**: 容量大，主流带宽 **4.8TB/s - 8TB/s**。参数必须反复从 HBM 搬运到 SRAM 参与计算 [cite: 67, 89]。

4. 选型建议

场景推荐型号核心优势

5. 资源配比

  • **隐形瓶颈**: 并发量大时，CPU负载过高或系统内存不足会导致 GPU 陷入饥饿 [cite: 117]。
  • **黄金比例**: 每 **1** 张 GPU 需配比 **16-32核 CPU** + **512GB-1TB 系统内存 (DRAM)** [cite: 118]。

💡 课堂精华 Q&A

  • **微调与蒸馏**: 知识蒸馏是大模型生成 `` 喂给小模型学习，其本质执行过程也是模型微调，两者不冲突 [cite: 1]。
  • **RAG 性能优化**: 当 RAG 向量超 **500万** 导致检索变慢时，部署分布式 RAG（增配节点并发检索）是有效方案。Embedding 模型选择可参考 ModelScope 榜单 [cite: 1, 2]。
  • **Agent 调优**: 优化智能体能力需定义好 Skills、Rules，并建立测试集进行评估。复杂电脑控制/视频生成任务推荐 API（如 qwen3.5-plus）或本地 `9B` 参数模型 [cite: 1, 2]。
  • **输出前端抖动**: LLM 生成超链接时 Markdown 渲染易抖动，建议先输出占位符（如 a1, a2），再单独生成链接注入 [cite: 2]。
  • **老旧硬件潜力**: 租用 A800 (**80G** 显存) 可以跑得动 `122B-Int4` 量化模型 [cite: 2]。

✅ 主流部署框架

1. 从请求级调度到 Token级调度

  • 早期框架采用请求级调度，等待整批处理完成，算力浪费严重 [cite: 137]。
  • 现代引擎核心创新：Continuous Batching (连续批处理)。细化到 Token 级别，请求B完成后，新请求E可立即无缝插入，极大提升 GPU 利用率 [cite: 138, 288, 304]。

2. CASE：Ollama 本地部署大模型

  • **双层架构**: Go 语言层管 API 与并发调度，C++ 层（`llama.cpp`）管底层矩阵算力 [cite: 281, 282]。
  • **特性**: 零依赖、跨平台，支持 GGUF 格式（4/8bit量化），适合快速验证与 CPU 边缘推理 [cite: 275, 276]。
  • **局限**: 缺乏 Continuous Batching，仅适合单用户调试，并发能力差 [cite: 286, 310]。

3. CASE：vLLM 高效部署

生产环境通用标杆，引入 **PagedAttention (页式 KV Cache)** 管理内存，支持千级并发 [cite: 315, 564]。

  • **核心启动参数**:
    --tensor-parallel-size: 分布式张量并行数 [cite: 317]。
    --gpu-memory-utilization 0.9: 显存分配比例 [cite: 389, 392]。
    --enforce-eager: 必须加，禁用 CUDA Graph 编译优化，避免 FakeTensorMode 报错 [cite: 388, 391]。
  • **工程隔离**: 建议在挂载盘通过 `python -m venv` 创建虚拟环境进行依赖隔离 [cite: 342, 343]。

4. SGLang 推理框架

定位为更快的 vLLM，PyTorch 官方生态项目。引入 RadixAttention (前缀树KV复用) [cite: 536, 537, 572]。

  • **性能**: 多轮对话、Agent 场景下前缀缓存命中率达 **75-95%**，长上下文吞吐量是 vLLM 的 **2-5倍** [cite: 550, 572]。
  • **优势**: JSON 结构化输出速度比 vLLM 快 **10倍**，百万日活下大幅节省 GPU 成本 [cite: 541, 547]。

⚙️ 结构化信息 (Outlines) & 格式约束

自由生成格式不稳定，Outlines库与vLLM内置机制可实现 **100%** 合法的结构化输出 [cite: 604, 605, 887, 888]。

  • **技术链路**: Pydantic 模型 $\rightarrow$ JSON Schema $\rightarrow$ 正则表达式 $\rightarrow$ **有限状态机 (FSM)** $\rightarrow$ 状态合并简化（跳过必然转移节点以节省采样算力） $\rightarrow$ Token 级匹配 [cite: 633, 646, 654, 699, 758]。
  • **vLLM 内置约束**:
    1. response_format 传 JSON Schema 约束结构 [cite: 918]。
    2. structured_outputs 传 Regex (如IP正则) 或 Choice 选项 [cite: 957, 979]。
  • **核心避坑**:
    ⚠️ 结构化仅保证**格式/字段合法**，不保证内部数值计算的绝对准确（需业务层二次核算） [cite: 969, 1042]。
    ⚠️ Qwen3 默认开启思考模式（输出 ``），会破坏 JSON 结构，必须通过 API 参数 `enable_thinking: False` 或 prompt 尾部加 `/no_think` 关闭 [cite: 897, 899, 903]。
