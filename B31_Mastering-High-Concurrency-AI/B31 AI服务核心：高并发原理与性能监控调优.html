✅ 1. 高并发 AI 服务的内存瓶颈

什么是 KV Cache？

自回归生成中，为避免重复计算，将每一层已计算的Key和Value张量缓存。高并发下，如200GB+的KV Cache远超A100显存，成为显存杀手。

KV Cache 的三大瓶颈

  • 内部/外部碎片：传统按最大长度预分配，实际回复极短时浪费严重，利用率常低于30%。
  • 动态长度浪费：不同请求长度不一，空闲显存块不连续导致无法分配给新请求。
  • Copy-on-Decoding：并行采样/Beam Search需复制整个前缀Cache，显存爆炸。

PagedAttention 机制

引入OS的虚拟内存思想，通过 Block Table 维护逻辑与物理地址映射。

  • 按需分配：16 tokens为一Block，用满再申请物理空间，消除内部碎片。
  • 写时复制 (COW)：多请求共享Prompt物理Block，遇分歧点再开辟私有空间，极大节省显存。
  • 动态重排：无需找连续大块显存，收集分散空闲Block即可，为 Continuous Batching 奠定基础。

✅ 2. vLLM架构实现详解

Batch 概念与困境

将多个请求打包送入GPU进行单次前向传播。传统静态 Batch 必须同步等待最长请求完成，导致GPU产生大量空转耗时。

静态 Batch vs Continuous Batching

  • Continuous Batching (动态批处理)：完成一个请求立即腾出位置，动态填入新请求。GPU始终满负荷，吞吐量提升2倍以上。

vLLM 的 Iteration-level Scheduling

细粒度到单次 Token 迭代的调度。每生成1个Token即处理新请求的Prefill、执行Forward并移除完成请求，彻底消灭同步等待死区。

PagedAttention 在 vLLM 中的实现

底层通过自定义CUDA Kernel，使得GPU多线程能并行读取分散在物理显存中的Block，高效合并内存访问请求。

✅ 3. 推测解码 (Speculative Decoding)

推测解码算法基础

  • 核心逻辑：小模型(Draft)快速"猜"出多个候选Token -> 大模型(Target)一次性"验证"并修正，保证输出质量无损。
  • Typical Acceptance：过滤掉大模型生成概率低但合理的词。基于信息熵判断，接受信息量贴近分布熵的Token。

MEDUSA 推理框架

  • 无独立小模型：在原LLM后冻结主干，追加多个 Medusa Heads 并行预测未来Token。
  • Tree Attention：生成树状候选结构，利用特殊Mask在单次前向传播中验证所有路径。

EAGLE 推理框架 (底层突破)

  • 特征级自回归：由于Token级预测不确定性高，EAGLE改在倒数第二层特征(Feature)上进行自回归，特征连续且极易预测。
  • 动态草稿树 (EAGLE-2)：摒弃静态树，根据上下文置信度动态剪枝和扩展分支，算力集中于高概率路径。
  • 突破大Batch衰减 (EAGLE-3)：独创 Training-time Test 模拟推理误差。在Batch=64的高并发场景下仍保持1.38x加速，打破了传统推测解码“高并发失效”的魔咒。

✅ 4. vLLM 性能监控与调优

核心评估指标与监控工具

  • TTFT (Time To First Token): 首字延迟，受长Prompt(Prefill阶段)影响最大。
  • TPOT (Time Per Output Token): 生成延迟，受显存带宽、Batch大小影响。
  • 监控工具：vLLM内置 Prometheus Metrics (关注 num_requests_running, gpu_kv_cache_usage 等)；深入底层可使用 Nsight Systems 进行 Kernel 分析。

核心调优参数与策略

  • 提升吞吐：拉高 max-num-seqs 与批处理tokens；启用 fp8 KV Cache量化。
  • 降首字延迟：开启 Chunked Prefill，将长Prompt拆分交错执行，避免阻塞。
  • 多轮对话优化：开启 enable-prefix-caching 复用历史会话显存。
  • 节省显存：限制 max-model-len，使用 FP8 精度存放 KV Cache。
  • 大Batch推测解码失效应对：当GPU接近Compute-Bound时，推测解码开销变大，此时可引入 PD分离 (Prefill / Decode 单独部署) 架构。

✅ 5. 课堂精华 Q&A

  • Q: 如何评估LLM并发数上限与优化？
    A: 通过阶梯并发(8/16/32/128)压测，监控吞吐量与TPOT的性能衰减拐点；优化需结合 Continuous Batching 与显存调配。
  • Q: 企业内部vLLM部署还需要哪些技术栈？
    A: vLLM仅作为底层推理的 API Endpoint。上层业务应用需结合 Agent 开发框架（如 LangChain / Qwen-Agent / LlamaIndex）来实现。
  • Q: 部署300B超大模型可行吗？
    A: 可以。单卡显存不足，需采用多卡（如8张A100）结合张量并行(TP)与流水线并行(PP)进行分布式部署。
  • Q: 知识库处理 Excel 和 PDF 的 Chunk 方案？
    A: PDF通常走 切片 -> Embedding相似度检索；Excel等结构化数据强烈建议采用 文本转SQL (Text-to-SQL) 进行精确查询。
  • Q: PDF中的表格如何提取更好？
    A: 推荐使用专用的解析工具（如 MinerU），将表格精准解析还原为 HTML 或 Markdown 格式，以保留原有的结构信息。
  • Q: 模型参数量与生成速度的关系？
    A: 强相关。在相同的部署环境下，模型参数量越小，单次前向传播的计算量就越低，生成速度自然越快。
